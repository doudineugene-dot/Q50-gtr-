# Q50 GTR+

Дополнительная приборная панель для штатного головного устройства
Infiniti Q50 2017 (InTouch / DCU Gen1).

**Версия:** 0.6 · **Экран:** 840×480, landscape · **Android:** API 9 (2.3)

> Совместимость с DCU ещё **не проверена**: приложение собирается и
> подписывается, но на автомобиль пока не устанавливалось.

## Что это

Одно окно, три вкладки, вся графика рисуется программно через
`android.graphics.Canvas`. Ни AndroidX, ни support library, ни Material —
ни одной сторонней зависимости вообще. Ни одного layout XML.

### Вкладки

| ДВИГАТЕЛЬ | ТОПЛИВО | ШАССИ |
|---|---|---|
| RPM, Boost actual | HPFP actual/target | Силуэт Q50 сверху |
| Охлаждающая жидкость | AFR B1/B2 | Давление по 4 углам |
| Температура масла | STFT B1/B2 | Ресивер |
| Давление масла | LTFT B1/B2 | АКПП, раздатка |
| Температура впуска | Boost actual/target | Борт. сеть, наружная T |

Нижняя строка (всегда видна): ignition timing, максимальный knock index,
положение дросселя, скорость.

Навигация: касание вкладки или горизонтальный свайп.

## Источники данных

Отрисовка ничего не знает о происхождении чисел. Каждое значение — это
`Channel` со своим состоянием:

| Состояние | Смысл |
|---|---|
| `LIVE` | реальные данные из машины |
| `STALE` | были реальными, свежих кадров нет |
| `DEMO` | синтетика для проверки интерфейса, всегда с бейджем DEMO |
| `UNAVAILABLE` | канал не логируется — рисуется «НЕТ ДАННЫХ», не число |

`DataHub` отдаёт приоритет живым источникам; `DemoDataProvider` работает
только пока ни один из них не подключён.

- `EcuTekSource` / `EcuTekLiveSource` — заготовка под EcuTek.
- `AirLiftSource` / `AirLiftLiveSource` — заготовка под AirLift Performance 3H.

Транспорт ни для одного из них **не придуман**: обе реализации честно
сообщают `isConnected() == false` и не пишут ни одного значения. Подключение
реальных данных — это работа внутри `poll()`, приборная панель не меняется.

### Чего в логе нет

- **LPFP** — низкое давление топлива в текущей конфигурации EcuTek не
  логируется. Канал есть, но постоянно `UNAVAILABLE`, и вкладка ТОПЛИВО
  прямо говорит об этом.
- **Turbo Speed** — не логируется на этой машине, поэтому в проекте
  отсутствует полностью.

## Сборка

Локальный Android SDK не нужен — всё собирается в GitHub Actions:

1. Actions → **Build APK** → Run workflow (или любой push в `main`).
2. Artifact **`Q50-GTR-Plus-v0.6-InTouch`** со страницы завершённого run.
3. Внутри: `Q50-GTR-Plus-v0.6.apk` и `.sha256`, `Q50-GTR-Plus-v0.6.epk` и
   `.sha256`, `signature.txt`, `badging.txt`, `epk-info.txt`,
   `BUILD-PROVENANCE.txt`.

`BUILD-PROVENANCE.txt` пишется сборкой и говорит, из какого коммита, тега и
run получились именно эти файлы, с их контрольными суммами и отпечатком
сертификата подписи.

Для установки в машину нужен `.epk` — см. раздел ниже.

### Почему не Gradle

Android Gradle Plugin не поддерживает `minSdkVersion 9`. Поэтому сборка идёт
классической цепочкой, как в проверенном на этом же головном устройстве
проекте [q50dash](https://github.com/doudineugene-dot/q50):

```
aapt -> javac --release 7 -> d8 --min-api 9 -> zipalign -> apksigner
```

- `build.sh` — сборка. Компиляция против `android-2.3.3.jar` (API 9), так что
  отсутствующий на Android 2.3 Android-API не пройдёт компиляцию.
- `verify.sh` — проверки готового APK: подпись, `aapt dump badging`,
  наличие `classes.dex`, отсутствие нативных библиотек, SHA-256.
- `build-epk.sh` — упаковка APK в `.epk` и строгая проверка контейнера.
- `provenance.sh` — `BUILD-PROVENANCE.txt` по готовым артефактам.

Оба скрипта запускаются и локально, если в `PATH` есть `aapt`, `zipalign`,
`apksigner`, `d8` и JDK 8–17.

### Совместимость

| | |
|---|---|
| minSdkVersion | 9 (Android 2.3) |
| targetSdkVersion | 10 |
| Java | `--release 7` (байт-код, читаемый d8/dx под Dalvik) |
| Зависимости | нет: ни AndroidX, ни support library, ни Kotlin |

Из `java.*` используются только `Math`, `Float`, `Integer`, `String`,
`StringBuilder` и `System.currentTimeMillis` — всё это есть в libcore
Android 2.3. Компилятор это **не** проверяет (сигнатуры `java.*` берутся из
JDK), поэтому за новыми зависимостями нужно следить вручную.

Манифест повторяет подход q50dash: `uses-sdk 9/10`, разрешение
`com.ygomi.permission.IVI_CAN_READ`, `ivi.isDistractive=false`,
`ivi.supportDisplay=ALL`. Атрибутов новее API 9 (`android:exported`,
`android:hardwareAccelerated`, `screenSize` в `configChanges`) нет.

### Подпись

Только **v1 (JAR signing)** — единственная схема, которую знает Android 2.3.
v2 и v3 выключены явно, подпись делается с `--min-sdk-version 9`, и
`verify.sh` падает, если схемы окажутся не такими.

Сборка работает в двух режимах и объявляет это явно — `SIGNING_MODE`:

| Режим | Когда | Что значит |
|---|---|---|
| `temporary` | обычный push / PR | ключ создаётся на раннере и выбрасывается |
| `persistent` | заданы секреты репозитория | ключ постоянный |

Публикация release разрешена **только** при `persistent`. Причина простая:
обновить поверх установленной копии можно лишь тем же сертификатом, а
одноразовый ключ каждый раз другой, и обновление не встанет. Если release
запускается без секретов, workflow падает **до** публикации.

Сверх того при публикации отпечаток сертификата сверяется с
`release-signing-cert.sha256`, и несовпадение тоже роняет сборку — чтобы
подменённый или пересозданный ключ не уехал в release незамеченным.

Как завести постоянный ключ — в [`keys/README.md`](keys/README.md).
В репозитории ключей нет и быть не должно.

## Что подтверждено, а что нет

### ПОДТВЕРЖДЕНО

- APK собирается под **API 9 / targetSdk 10** — проверяется `aapt dump badging`,
  сборка падает при других значениях.
- Подпись **v1 (JAR signing)** присутствует.
- **v2 и v3 выключены** — тоже проверяется, а не подразумевается.
- Контейнер `.epk` имеет **корректную структурную раскладку** — те же 16
  инвариантов проходят и на двух реальных образцах `.epk`, собранных не нами.
- **CI проходит** целиком: APK build → APK verify → EPK build → EPK verify →
  provenance → artifact.

### НЕ ПОДТВЕРЖДЕНО

- **Фактический запуск Q50 GTR+ v0.6 на этом DCU.** Приложение в машине не
  запускалось ни разу.
- **Совместимость текущего OBU-сертификата с этим конкретным Q50 2017.**
- **Реальные данные EcuTek** — сейчас их нет, источник возвращает
  `isConnected() == false`.
- **Реальные данные AirLift** — то же самое.

Всё, что показывают приборы, — демонстрационные значения с бейджем DEMO.

## EPK — установка на головное устройство

AppManager (`com.connexis.appsmanager`) устанавливает приложения с USB
**только** из контейнера `.epk` — голый APK он не распознаёт. Поэтому сборка
выпускает оба файла, и для машины нужен именно `Q50-GTR-Plus-v0.6.epk`:
положить в корень флешки FAT32 и выбрать в AppManager.

### Что подтверждено

Формат и алгоритм упаковки **подтверждены**: раскладка контейнера, режим
шифрования и обёртка ключа сверены с открытой реализацией и с разбором
реальных образцов `.epk`. Подробности — в [`docs/epk-format.md`](docs/epk-format.md).

| | |
|---|---|
| magic | `.epk` |
| version | 2 |
| payloadType | 2 |
| blockCount | 1 |
| keySize | 128 (RSA-1024) |
| обёртка ключа | RSA PKCS#1 v1.5 |
| шифр нагрузки | AES-256-CBC |
| IV | фиксированный `01 23 45 67 89 ab cd ef 00 00 00 00 00 00 00 00` |
| паддинг | PKCS5 |
| имя внутри контейнера | `q50gtr.apk` |

`build-epk.sh` собирает контейнер, а `tools/epktool.py verify` проваливает
сборку, если хоть одно из этих полей не такое, если имя внутри не ASCII или не
`q50gtr.apk`, если длина шифротекста не кратна 16, если область добивки ключа
не нулевая или если расчётный размер контейнера не совпал с реальным.

### Что НЕ подтверждено

Публичный сертификат [`keys/obu_cert.pem`](keys/README.md) — типовой сертификат
InTouch, а не сертификат конкретно вашей машины. `.epk` примет только то ГУ, в
прошивке которого лежит **парный закрытый ключ**.

> EPK контейнер технически сформирован корректно.
> Совместимость OBU certificate с конкретным DCU Infiniti Q50 2017
> будет подтверждена только установкой на автомобиле.

Если сертификат не подойдёт, его нужно заменить своим — как это сделать,
написано в [`keys/README.md`](keys/README.md).

### Ключи

Для сборки `.epk` нужен **только публичный сертификат**. В формате нет подписи,
сеансовый `dataKey` заворачивается открытым ключом — поэтому закрытый ключ OBU
для сборки не требуется и в репозитории его нет. Закрытый ключ понадобился бы
только чтобы распаковать чужой `.epk`.

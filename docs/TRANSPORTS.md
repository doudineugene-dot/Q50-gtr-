# Четыре пути телефон → ГУ: что доказано, что нет

> **Обновлено после глубокой разведки. Картина изменилась.**
>
> ```
> Bluetooth: Core ver 2.15
> Bluetooth: HCI device and connection manager initialized
> Bluetooth: HCI socket layer initialized
> модули: bnep, cdc_ether, cdc_acm, usbserial, usb_wwan, option
> su -c id -> uid=0(root) groups=...,net_bt_admin,net_bt,inet
> /sys/class/bluetooth ПУСТ -> HCI-контроллеров нет
> usb6: ehci_hcd EHCI Host Controller
> 3-2: TEPCO UQUEST MatrixQuestUsb func ECM
> /dev/bus/usb ЕСТЬ (usbfs)
> службы: android.hardware.usb.IUsbManager, android.net.ethernet.IEthernetManager
> ```
>
> Ядро **умеет** Bluetooth: стек поднят, HCI-сокеты работают, BNEP
> загружен. Не хватает только контроллера — он на соседнем модуле.
>
> USB-host работает, usbfs на месте, и `audio0` оказался **USB-устройством
> CDC-ECM**: ГУ уже сейчас гоняет Ethernet поверх USB к соседнему блоку.
> Драйвер `cdc_ether` загружен, служба `IEthernetManager` зарегистрирована,
> root даёт uid=0.
>
> Это переводит путь C из «почти закрыт» в **самый вероятный**.

Сводка по состоянию на текущий замер. Колонка «доказано» означает
«снято на самом устройстве», а не «следует из документации».

## A. Телефон → ГУ по Bluetooth Classic

**Доказано:** невозможен. В Android-слое ГУ Bluetooth отсутствует —
`getDefaultAdapter()` возвращает null из обоих потоков,
`hasSystemFeature(android.hardware.bluetooth)` даёт false,
`getSystemService("bluetooth")` даёт null, в реестре служб нет
bluetooth, в `getprop` нет ни одного свойства, пакетов нет.

**Не проверено:** есть ли HCI-контроллер в ядре. Каталог
`/sys/class/bluetooth` существует, но его содержимое раньше не
перечислялось — а значение имеет только оно. Пустой каталог означает,
что контроллера нет физически и обойти это нечем, в том числе с root.

**Нужный тест:** страница ТРАНСПОРТ новой сборки, строка
«контроллер Bluetooth в ядре».

## B. Телефон → ГУ по Wi-Fi/TCP

**Доказано:** невозможен. `/sys/class/net` содержит ровно `audio0` и
`lo`. `audio0` — внутренняя шина к аудио-подсистеме с link-local
адресом `169.254.11.1`, телефону она недоступна. Устройства `wlan`
в ядре нет, то есть Wi-Fi-железа нет вовсе.

**Не проверено:** ничего существенного. Отсутствие сетевого устройства
в ядре — окончательный ответ.

**Приёмник готов:** `BridgeSource`, UDP 45455, формат в
`docs/PHONE-BRIDGE.md`. Заработает без правок, если данные когда-нибудь
пойдут с другого устройства.

## C. Телефон → ГУ по USB

**Доказано:** ГУ работает с USB-накопителями — через них ставится
`.epk`. Значит host-контроллер в системе есть.

**Не проверено:** видно ли шину из Android (`/sys/bus/usb/devices`), есть
ли gadget-контроллер (`/sys/class/udc`) и usbfs (`/dev/bus/usb`).

**Ограничение, известное заранее:** Android USB Host API появился в API
12, здесь API 10. Работать с устройством из Java-приложения штатными
средствами нечем. Через usbfs это требует ioctl USBDEVFS, а значит
нативного кода — в проекте, собранном без NDK, этого нет.

**Что реально возможно:** файловый обмен. ГУ читает флешку. Это не живая
телеметрия, а перенос файлов, и как канал для приборов не годится.

**Нужный тест:** страница ТРАНСПОРТ, раздел USB.

## D. Внешний USB-адаптер BLE на ГУ

**Доказано:** ничего.

**Требуется одновременно:** host-контроллер (вероятно есть), драйвер
btusb в ядре, поднятый стек Bluetooth в системе и программный интерфейс
к нему. Последних двух нет — это показано в пункте A. Модуль btusb в
`/proc/modules` тоже стоит проверить, но даже его наличие не даст
приложению API.

**Вывод:** путь требует вмешательства в прошивку, что прямо запрещено.

## Общий итог

Три из четырёх путей закрыты замерами. Четвёртый упирается в запрет на
изменение прошивки. Новая сборка закрывает последние незакрытые клетки
таблицы — наличие HCI-контроллера и состояние USB-подсистемы.

Отдельно стоит помнить: даже открытый транспорт **не даёт протокола**.
Публичного API у ECU Connect нет; приложение умеет только вручную
делиться файлами логов через почту или облако
([EcuTek: Datalogging](https://ecutek.atlassian.net/wiki/spaces/SUPPORT/pages/327690/ECU+Connect:+Datalogging),
[ECU Connect: My Files](https://ecutek.atlassian.net/wiki/spaces/SUPPORT/pages/327712/ECU+Connect:+My+Files)).
Значит мост через телефон требует **собственного клиента EVI** —
разобранного BLE/GATT-протокола EcuTek. Это отдельная задача, и она не
решается ни одним из четырёх транспортов.

# Air Lift Performance ALP3: почему прямая интеграция невозможна

## ИТОГ: на этом ГУ ALP3 не запустится — доказано установочной проверкой,
## а не догадкой о протоколе

Официальное приложение Air Lift Performance 3 (`com.airliftcompany.alp3`,
последняя публично распространяемая версия — 1.7.0, та же, что упомянул
пользователь) требует Android заметно новее, чем стоит на этом ГУ:

```
ГУ:    Android 2.3.7, API 10
ALP3:  минимум Android 7.0 (API 24) по данным площадок распространения APK;
       на собственном сайте Air Lift Performance разработчик указывает
       Android 5.0+ как нижнюю границу для линейки приложений 3H/3P
```

Источники (доступ к play.google.com и apkpure.com из этой машины закрыт
сетевым прокси — Google Play напрямую не проверить; ниже — то, что удалось
получить через поиск):

- [Air Lift Performance 3 — Google Play](https://play.google.com/store/apps/details?id=com.airliftcompany.alp3&hl=en_US)
- [Air Lift Performance 3H/3P Android Mobile App](https://www.airliftperformance.com/blog/air-lift-performance-3h-3p-android-mobile-app)
- [Air Lift Performance 3 — APKPure](https://apkpure.com/air-lift-performance-3/com.airliftcompany.alp3)
- [Air Lift Performance 3 1.7.0 — mi9.com](https://mi9.com/package/com.airliftcompany.alp3)

Даже беря самую мягкую цифру из двух (Android 5.0, API 21), она всё равно
выше API 10 этого ГУ. Здесь неважно, какой транспорт использует манифолд —
BLE, классический Bluetooth или что-то ещё. **Android проверяет
`minSdkVersion` на этапе установки, до первого байта, отправленного по
Bluetooth.** APK с `minSdkVersion` выше системного `PackageManager`
отклоняет — это документированное поведение платформы, а не предположение
о поведении конкретного приложения. Установка ALP3 через App Garage на этом
ГУ не была даже опробована, потому что результат этой проверки не зависит
от попытки: несовместимость видна из метаданных пакета.

Это тот же вывод, что и для EcuTek (`docs/ECUTEK-EVI-6087.md`), но
установленный по другой причине. Для EcuTek дело было в отсутствии
Bluetooth на этом слое Android (шесть независимых проверок). Для ALP3
дело ещё проще: даже если бы Bluetooth на ГУ был, само приложение
физически не запустится на API 10.

## Официальные интерфейсы интеграции — их нет

Air Lift Performance не публикует ни SDK, ни документированный API, ни
схему Intent, ни ContentProvider для ALP3. Публичного протокола манифолда
Airlift578e (BLE-характеристики, формат кадра) в открытом доступе не
найдено — ни на сайте производителя, ни в GitHub, ни в форумах реверс-
инжиниринга BLE-устройств. Это подтверждает то, что пользователь уже сказал
прямо: подтверждённого дампа протокола пока нет. Выдумывать его здесь не
будет — как и раньше с EcuTek.

## Значит — только через телефон

Раз APK не запускается на ГУ, а протокол манифолда не разобран, прямой путь
закрыт по обеим причинам сразу, а не по одной. Официальный ALP3 работает на
телефоне (Samsung Galaxy S21 FE, современный Android) уже сейчас — значит
приложение должно оставаться на телефоне, а на ГУ попадать то, что оно
показывает. Это и есть второй этап: не подключение к манифолду с ГУ, а
трансляция уже работающего интерфейса телефона на экран ГУ по уже
доказанному двустороннему UDP-мосту (`docs/PHONE-BRIDGE.md`).

Собственный источник данных (`AirLiftLiveSource`, канал `AIRLIFT`) остаётся
отдельной, ещё не реализованной возможностью — она появится, когда протокол
манифолда будет подтверждён по `btsnoop_hci.log`, а не раньше. До этого
момента трансляция экрана и «настоящий источник данных» — два разных пути,
и смешивать их нельзя: числа с картинки в каналы `DataHub` не идут.
